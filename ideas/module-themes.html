A theme for every module

The whole site changes its look on the day a new module starts. A design module should not look like a back-end module.

  • Kind of work: visual identity, design tokens, CSS architecture, accessibility testing
  • You'd enjoy this if: you like building a system that other people can design inside, and you care about both colour and code

Why this is worth doing

The school site looks the same on every day of the programme. A new module is a real change for them: new subject, new project, new kind of thinking. Today the site does not mark that moment at all. A theme that arrives on the first morning of a module says "something new starts today" before anyone has read a word.

It is also a teaching tool. The site is the one product every student uses, so it is the best place to show what a design system is. If the back-end module looks like a terminal and the design module looks like a poster, students can open the dev tools and see how a few variables did that.

For you, the interesting part is the system under the themes. One theme is a styling job. Six themes that all stay readable, switch on a date, and can be designed by someone who is not you: that is a design systems project, and it is the kind of work that looks strong in a portfolio.

Where we are today

The good news first. The site already uses CSS custom properties for almost everything. There is one global stylesheet with a set of variables on :root: a black-to-white ramp, one brand colour in five steps, status colours for success, failure, warning and pending, a radius scale, a type scale, and six accent colours for guide sections. Components are written with styled-components and read those variables with var(). So changing a value in one place already changes it across the site.

The brand colour is the best clue. Its variable is called --theme-module3-100, and the same violet is used for every module, in more than two hundred places. The name suggests that somebody once planned a colour per module and stopped after one. You would be finishing an old idea.

There is also a small theming system already in the code, in a different corner. Each project brief under /projects has its own theme: eight colours and two fonts, checked and then applied as CSS variables on that page. The back-end brief uses a dark green cover with a monospace heading font, and the first-website brief uses warm paper with a red accent. So "a module has a look" exists for the briefs. It stops at the brief pages and does not reach the rest of the site. The video cards on the resources page also have a colour per module, written directly into that component.

Now the hard parts, honestly:

  • The variable names describe colours, not jobs. --primary-white is used both as a card background and as text on a coloured button. --primary-black-100 is used as text. For a theme that only changes the accent this is fine. For a dark theme it is a problem, because "white" would have to become dark in one place and stay light in the other.
  • Some colours are not variables at all. About twenty files have colours written as hex values, and the page background is one fixed SVG image. A theme switch would not reach those.
  • There is no dark mode and no theme switch. Nothing reads prefers-color-scheme, and there is no data-theme attribute or theme provider. Several components do respect prefers-reduced-motion, which is a good habit to keep.
  • The calendar does not know when a module starts. It has events (with categories like milestone, lecture, deadline and holiday) and one active term with a start date, an end date and an optional date for the second half. Guides know which module they belong to, with a title and a number. Nothing connects the two. "The day the calendar says the module begins" needs a new piece of data, and somebody has to decide where it lives.

My honest estimate: an accent-only theme per module is a small job, maybe a week including the date logic. A full theme with its own background, type and dark variants means renaming the variables by role first, and that touches almost every styled file. That part is slow and careful work, and it is the part that makes everything after it easy.

What the research says

Theming is well understood by now, and the browser has become much better at it in the last two years. These are the findings that change how you would build this.

Linear went from 98 variables per theme to 3

When Linear rebuilt its themes it stopped defining 98 values by hand. A theme is now a base colour, an accent colour and a contrast setting, and the rest is calculated in the LCH colour space. Six module themes are much easier to keep healthy if each one is three decisions and not ninety-eight.

Source: Linear, "How we redesigned the Linear UI"
OKLCH makes lightness predictable

In HSL, two colours with the same "lightness" can look very different, so every new hue needs new contrast checks. OKLCH uses perceptual lightness. You can keep the lightness steps fixed, change only the hue per module, and the contrast stays close to what you tested.

Source: Evil Martians, "OKLCH in CSS"
The contrast rule is strict: 4.5 to 1

WCAG asks for 4.5:1 for normal text and 3:1 for large text, and the number is not rounded: 4.499 fails. The current stylesheet already has a note about an amber label that came out at 3.08:1 and had to be darkened. With six themes, a person cannot check this by eye. It has to be a test that runs for every theme.

Source: W3C, Understanding WCAG 2.2, Contrast (Minimum)
WCAG 2 contrast is weak for dark themes

The author of APCA, a newer contrast method, argues that the WCAG 2 formula overstates contrast for dark colours, so a pair can pass at 4.5:1 and still be hard to read near black. APCA is a candidate for WCAG 3 and not a finished standard. A sensible rule for a dark terminal theme: pass WCAG 2 because it is the rule, and use APCA as a second opinion.

Source: APCA documentation, "Why APCA"
Design tokens have a stable standard since October 2025

The W3C Design Tokens Community Group published its first stable format, version 2025.10. It covers themes and modes without copying files, and supports Oklch and Display P3. If you store themes as token files, you no longer have to invent your own format, and tools like Style Dictionary, Tokens Studio and Terrazzo can read them.

Source: W3C Design Tokens Community Group
Animated theme changes now work in every modern browser

document.startViewTransition() has been in all the latest browsers since October 2025. The default effect is a cross-fade between the old and the new look, and in a browser without support the change just happens with no animation. The "new module" moment can be a real reveal with very little code.

Source: MDN, Document.startViewTransition()
The browser can pick text colour for you, with limits

contrast-color() returns black or white for a given background and reached all the latest browsers in April 2026. MDN warns that mid-tone backgrounds do not give enough contrast with either one. So it helps for buttons on strong colours, and it does not replace testing your themes.

Source: MDN, contrast-color()

How it could be built

These are layers more than rivals. The first one is needed in every case, and you choose how far to go after it.

Role tokens and one attribute

Rename the variables by job: --surface, --text, --text-on-accent, --accent, --border. Each module then overrides them in a block like [data-module="5"] { … }. The root layout already runs on the server for every request, so it can work out today's module and put the attribute on <html> before the page is sent.

No new library, no JavaScript in the browser, and no flash of the wrong theme because the server decides. It works with styled-components, with the CSS modules in the portfolio builder, and with whatever comes later.

The rename touches almost every styled file. Do it as a plain refactor with no visual change first, and compare screenshots before and after. Then add themes.

Themes generated from a few choices

Follow Linear: a module theme is a hue, a mood (light or dark) and maybe a heading font. Everything else is calculated. You can do it in CSS with oklch(), color-mix() (already used in a few places on the site) and relative colours, or in a small script with Culori, Leonardo or Google's Material Color Utilities (Apache 2.0), which builds a whole scheme from one source colour.

A theme becomes a tiny record that fits in MongoDB next to the term. A teacher, or a student, could make one in a form with a live preview, and the system keeps it readable.

Generated palettes are safe and can look a little the same. The identity then has to come from type, illustration and motion. Decide early how much a designer may override by hand.

A token pipeline from Figma

Design the themes as variable modes in Figma, one mode per module. Export them in the Design Tokens format and let Style Dictionary or Terrazzo build the CSS file. The token files live in the repository and are reviewed like code.

Designers work where they are comfortable, design and code cannot drift apart, and it is how larger teams really work. A cohort could deliver a theme as one JSON file.

More moving parts for a small school. The number of modes in Figma depends on the plan, so check what the school's plan allows before you depend on it. A new theme needs a build and a deploy.

More than colour: a theme kit

A theme is also a background illustration (today one SVG for every page), a heading font, the shape of corners (the radius scale is already a set of variables), a small set of motion values and perhaps an opening animation on day one, built with the View Transitions API.

This is where a design module really stops looking like a back-end module. Colour alone will not get you there.

Keep the layout fixed. Navigation, spacing and the meaning of the status colours must not move, or students have to learn the site again every few weeks. Fonts cost loading time, and every animation needs a calm version for prefers-reduced-motion.

A first week

  1. Make an inventory Go through the global stylesheet and list every variable and what it is used for. Search for hex colours outside it. Mark each one: already a variable, easy to convert, or special. You will know the real size of the job by the end of the day.
  2. Break it on purpose In the browser dev tools, change the brand colour and the white and black variables on :root to something loud. Click through the home page, a guide, the calendar and the groups page. Screenshot every place that did not change or became unreadable. That list is your backlog.
  3. Write the role names on paper Agree on 12 to 20 token names by job before you touch code. Use the Radix scale as a checklist: do you have a name for a hovered background, a border, text on a solid colour?
  4. Design two opposite themes Pick the two modules that are most different, for example a design module and the back-end module, and design one screen in each. Two extremes will test your token names better than six similar palettes.
  5. Prototype the switch On a branch, put a data-module attribute on the page and make one section of the site react to it. Add a temporary dropdown so you can flip themes and show people.
  6. Sit down with Smári about dates Bring one question: where does "module 4 starts on this date" live, and who types it in? Sketch the smallest change to the term settings that would answer it.

Still open

  • If two cohorts are in different modules on the same day, which theme does each person see? And what does a teacher see, who teaches both?
  • How far may a theme go? Accent colour only, or background, type and illustration too? Where is the line between "the site looks new" and "I cannot find the button"?
  • Should the status colours (green for passed, red for failed, orange for act now) be locked in every theme? What happens when a module's own colour is red?
  • Does every module theme need a light and a dark version, so that it can follow prefers-color-scheme? That doubles the design and testing work. Or is "dark" simply the look of one module?
  • Can a student turn the theme off, or keep a favourite from an earlier module? Is the shared moment worth more than personal choice?
  • Who designs the themes after you leave? Could designing next year's theme for a module be an assignment for the cohort that just finished it, with the contrast test as the only gatekeeper?
  • Do public pages, like the open guides and the gallery, change too? A visitor from a search engine has no idea what module it is.
